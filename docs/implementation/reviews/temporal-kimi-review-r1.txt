  ## 发现（按严重性排序）

  ### KIMI-01（高）时间参数的显式 Precision 无契约；越界 Scale 会被位域掩码误译

  - 计划位置：§4.2（精度规则）、§5 决策次序 2、§7 TP-A05。§5 只冻结"用户是否显式设置 Scale（包括 0）"，全文未出现 Precision 的时间语义。
  - 源码与证据：
    1. 官方驱动的七位写入惯用法是 **Precision=7、Scale 不显式设置**（`tools/TemporalPrecisionProbe/README.md`："O 使用公开 DbType.DateTime2/DateTimeOffset 参数（Precision=7、Scale未显式设置）"）。从官方驱动移植的应用会照此写法，计划却没有定义 W 对显式 Precision 的接受/拒绝/忽略规则。
    2. `DmParameter.do_Scale` setter 无范围校验（`src/W.DmProvider/PublicApi/DmParameter.cs:333-345`，byte 任意值可入）。
    3. `DmTemporalCodec.ValidateFraction` 对**用户输入的 Scale** 也套用 wire 位域解码：`encodedScale > 9 ? encodedScale & 0xF : encodedScale`（`src/W.DmProvider/Internal/Types/DmTemporalCodec.cs:82`）。后果：显式 `Scale=19` 被静默当成 3，`Scale=23` 在已验证 profile 上被当成 7——即计划承诺的"高于 wire 能力明确拒绝"对 16…31 段的 Scale 不成立，七位门可被 Scale=23 意外打开。TimeSpan 路径（同文件 :48-49）同类。
    4. Precision 处理在两条路径不一致：advisory 分支 `paraVal.SetPrec(prec)` 采用显式值（`DmSetValue.cs:1304-1316`），fixed describe 分支（typeFlag==1，case 26 于 :1343-1346）不回写 Prec，显式 Precision 被静默忽略。而 extended 类型的 describe precision 实际是**线字节长度**（9/11，见 `FixedTemporalBindingTests` :42-43），用户惯用的 Precision=7 与之语义错位。
  - 具体失败场景：移植代码设 `Precision=7` 写 TIMESTAMP(7) 固定列——实现者要么把 7 写进线描述符（未验证的线语义，服务器行为未知），要么静默忽略（用户以为控制了精度实际没有），两种都未被计划禁止或要求；另一实现者设 `Scale=23`  expecting 拒绝，实际按 7 通过，或设 `Scale=19` expecting 拒绝，实际按 3 拒绝合法值——错误消息与用户输入完全对不上。
  - 最小修订建议：§4.2/§5 增加两条——(a) 用户显式 Scale 先做 0…9 范围校验（CLR 可表示上限另按 profile 收敛到 7），越界抛 `NotSupportedException`/`ArgumentOutOfRangeException`，**用户 Scale 永不进入位域掩码解码**（掩码只用于 wire/described scale）；(b) 明确定义时间参数显式 Precision 的语义（建议：fixed describe 下显式 Precision 若不等于 describe/wire 要求值即拒绝，advisory 下拒绝或忽略二选一，写入计划；是否把 Precision 作为小数位别名由 TP-01 对 O 的线行为取证后决定）。TP-A05 增加 Scale=0/3/6/7/8/9/19/255 × legacy/extended × fixed/advisory 及 Precision 未设/7/9 的验收行。

  ### KIMI-02（高）TIMESTAMP WITH LOCAL TIME ZONE 全文缺席，与 §4.3 的笼统陈述冲突

  - 计划位置：§3 范围、§4.2 类型表、§4.3（"写 DateTime 不隐式转本地时间或 UTC"）、§7 全部矩阵——均未提及 LOCAL TIME ZONE。
  - 源码证据：TLTZ 是真实存在的服务器类型，且编码在 scale/prec 标志位里：`DmDateTime.NTYPE_IS_LOCAL_TIME_ZONE`（cType==16 且 `0x1000` 位，`DmDateTime.cs:110-117`）；写侧 `encode()` 对 `mask==4` 做 `transformTZ`（:1825-1841）；读侧 `decode()` 同样转换（:1671-1674）；`GetTimestamp` 对 TLTZ 按会话时区平移（`DmGetValue.cs:570-573`）。`NTYPE_IS_LOCAL_TIME_ZONE` **只认 cType 16**——extended 26 是否可携带 `0x1000` 未知（待验证）。
  - 具体失败场景：统一 codec 按"scale 位域必须先按具体类型解码"重写时，`0x1000` 标志被当作纯 scale 位处理或丢弃——TLTZ 列读回数据库时区的墙钟而非会话时区墙钟，**静默返回错误值**（数值校验全部通过，任何 ticks 断言若在同时区环境运行还发现不了）；或者 §4.3 的"不隐式转本地时间"被机械执行到 TLTZ 上，破坏其定义语义。两种都直接导致数据正确性回归。
  - 最小修订建议：§3/§4.2 显式点名 TLTZ：要么"保持现有会话时区转换语义"，并在 §4.3 加 carve-out（TLTZ 按类型定义做会话↔数据库时区转换，不属于被禁止的隐式转换），要么声明本专项不支持并在读写两侧明确拒绝；TP-01 增加探测项：16 的 TLTZ describe 标志形态、26 是否可携带该标志、会话/数据库时区不同时的往返；TP-A 矩阵加 TLTZ 行（写入、跨时区会话读回、标志位解码）。

  ### KIMI-03（中）8/9 位列的读侧契约未定义：GetString 与 typed getter 现状就是分叉的

  - 计划位置：§4.1（"CLR getter 抛 OverflowException；字符串路径不能通过已损失精度的 DateTime 拼回原值"）、§7 TP-A02/A06。计划暗示了方向，但从未写明哪个入口必须保留精确文本。
  - 源码证据：读侧存在两套解码——typed getter 经 `DmTimeFromRec4`/`DmDtDecodeFast`，`ns % 100 != 0` 即 `OverflowException`（`DmDateTime.cs:1224-1226`）；GetString 经 `valueOf`/`decode` + `ValidateWireNanoseconds`（`DmTemporalCodec.cs:91-100`），8 位列 ns 尾数非 0 也可通过，再由 `formatMilliSecond` 截位输出**精确**文本（`DateUtil.cs:13-26`）。`GetValue`→`GetObject`→`GetTimestamp` 走前一路径，即同一个 8 位非整 tick 值：`GetDateTime`/`GetValue` 抛、`GetString` 精确返回。
  - 具体失败场景：实施者"统一"读路径时若统一成拒绝——用户丢失对 8/9 位服务器值**唯一的精确读出通道**（这本身是一种数据可用性损失）；若统一成容忍——又容易滑向截断成 7 位（静默精度损失，直接违反 §1 目标）。计划对此无断言，两种错误都能在现有矩阵下"通过"。schema（`GetColumnSchema`/`GetDataTypeName`）对 8/9 位列的报告形态同样未钉死。
  - 最小修订建议：§4.1/§4.4 写明分层契约——`GetString`（及 provider-specific 文本投影）必须对 8/9 位列返回 wire 精确文本（不经 DateTime）；`GetValue`/`GetDateTime`/`GetFieldValue<DateTime|DateTimeOffset>` 对 CLR 不可表示的纳秒抛 `OverflowException`；schema 报告真实 scale 8/9。TP-A02 按"getter × 8/9 位 × ns%100 = 0/非0"补验收行。

  ### KIMI-04（中）§5.3 默认升级措辞与 §5.4 存在可读出矛盾的歧义；显式 DbType.DateTime 的 wire 选择未定

  - 计划位置：§5.3（"显式 DbType.DateTime2/Scale=7 及 CLR DateTime 的完整 ticks 诉求，在已验证 profile 上选择 extended wire/七位"）对照 §5.4（"不得按每次值的小数尾数在 16/26 间切换"）。§10 已承认默认推断切换是可观察行为变化，但切换的精确边界没写。
  - 源码证据：`DbType.DateTime` 与 `DbType.DateTime2` 映射到同一 provider 类型（`DmSqlType.cs:750-752`），ResolveType 之后二者**不可区分**，只有冻结的 `DmParameterMetadata.DbType`（`DmCommandPlan.cs:174-185`）保留原值——计划未说明 DateTime/DateTime2 的区分必须取自冻结 metadata。当前默认 CType 16（`DmSqlType.cs:612-613`）；advisory 绑定时以客户端选择类型覆盖（`FixedTemporalBindingTests.AdvisoryMetadataStillUsesTheSelectedClientType`）。
  - 具体失败场景：实现者 A 把"完整 ticks 诉求"读成按值选择（值有第七位才走 26）→ 直接违反 §5.4，prepare 类型随参数值漂移；实现者 B 把显式 `DbType.DateTime`（无 Scale）也升级到 26/7 → 存量应用的 datetime 参数 wire 类型突变（固定列 describe 为 16 时虽能兼容族内放行，但 advisory/裸表达式场景服务器隐式转换行为改变）；实现者 C 让显式 DateTime 永远停在 16/6 → 七位值被拒且无任何指引。三种实现都"符合计划"。
  - 最小修订建议：§5.3 改写为明确的**按 profile 稳定**规则，例如：推断 CLR DateTime/DateTimeOffset 与显式 DateTime2 或显式 Scale=7 → 已验证 profile 选 extended/七位；显式 `DbType.DateTime`（无 Scale）保持 legacy 16/6 默认，七位值拒绝并在消息语义上指向 DateTime2（最终取向由 root 定，但必须定）；补一句"DateTime 与 DateTime2 的区分取自冻结的原始 DbType，不取 provider 类型"。TP-A05 增加 推断/显式DateTime/显式DateTime2/Scale覆盖 四组合行。

  ### KIMI-05（中低）DateTimeOffset 双范围校验的责任方与数值边界未固定

  - 计划位置：§4.3（"同时校验服务端允许的偏移与 .NET 的 UTC 可表示范围"）、§4.4（值转换失败 OverflowException）、TP-A03（"边界拒绝"）。
  - 源码证据：当前只校验偏移量绝对范围，且区间不对称（`<= -780 || > 840`，即 (-13:00, +14:00]，`DmTemporalCodec.cs:42-43`）；.NET `DateTimeOffset` 构造本身已保证 UTC 在 CLR 范围内，因此真正未定的是**服务器侧**的双重范围（本地字段、以及 local−offset 对应的 UTC 瞬时都须落在服务器日期域内），当前代码无此检查。恰好 -13:00 被拒、.NET 允许到 -14:00，是否符合服务器实际范围——待验证。
  - 具体失败场景：`DateTimeOffset(0001-01-01 00:30, +14:00)`（UTC 落在公元前）驱动不预检 → 服务器拒绝返回 `DmException`，与 §4.4"值转换失败 OverflowException"和 TP-A03"边界拒绝"的断言形态冲突；或者实现者按猜测的服务器范围预检，拒掉服务器本来能表示的值。MaxValue + 正偏移、MinValue + 正/负偏移的服务器行为完全未知。
  - 最小修订建议：TP-01 必测项补"23/27 的偏移量程与 UTC 双重范围边界（含 MaxValue/MinValue × 极限偏移）"；§4.3/§4.4 写明：驱动预检偏移量程与本地 ticks 范围（取自 profile 表），UTC 越界是驱动预检（OverflowException）还是映射自具名服务器错误——二选一写死；TP-A03 按边界逐格断言。

  ### KIMI-06（低）TIME 的 24:00 读侧结果与 TIME(n>6) 探测未定义

  - 计划位置：§4.2 TIME 行（"24:00 不取模为次日零点"）——只说了不做什么，没说明行为是什么；TP-A04 无对应用例。
  - 源码证据：线格式小时位域 5 bit（`DmTime.cs:8-10`、解码 `hour & 0x1F`），24 可表示；现状读 hour=24 会在 `BuildDateTime` 经 `ArgumentOutOfRangeException` 包装为 `OverflowException`（`DmDateTime.cs:912-918`）；写侧 CLR 类型无法构造 24:00（TimeOnly 上限 23:59:59.9999999；codec 要求 date==MinValue）。
  - 具体失败场景：实施者"修复"24:00 时取模成 00:00（静默损坏）或进位次日（同样错误）；或让裸 `ArgumentOutOfRangeException` 漏出，破坏 §4.4 异常分类。TIME(7+) 列若服务器支持，写侧今日能干净拒绝（digits 7 > wireMaxScale 6），但读侧线格式未知。
  - 最小修订建议：§4.2 写明"读 hour=24 → OverflowException（值转换失败），不取模、不进位"；TP-01 确认该 profile 的 TIME 是否可返回 24:00:00、是否存在 TIME(n>6)（不存在则标记 profile-closed）；TP-A04 补行。

  ### KIMI-07（低）getter × 列类型矩阵的现状不一致未被固定为目标态

  - 计划位置：§2（"验证所有路径…一致性"）、TP-A06。计划的"一致性"没有逐格定义，而现状是参差的。
  - 源码证据：`GetTimestamp`（GetDateTime 落点）对 23/27 列返回 `GetTimestampTZ().DateTime`——**静默丢弃 offset**（`DmGetValue.cs:575-577`）；`GetDate` 只支持 14/16/23，不支持 26/27（:605-619，扩展列抛 InvalidCastException）；`GetTime` 支持 15/16/22/23，同样不含 26/27（:622-646）；TIME 列 `GetValue` 的返回类型受连接属性 `DbTimeToTimeSpan` 影响（:788-794），且 TimeSpan 模式走 `GetTimeInString` + `ParseExact` 字符串中转（与 §1"消除字符串中转"目标相关）。
  - 具体失败场景：统一化若顺手把"GetDateTime 遇 TZ 列"改成抛异常——可观察行为回归，直接打到 R1 消费者与 EF；若保持参差——扩展列上 `GetDateTime` 可用而 `GetDate` 抛，TP-A06"值、类型、异常一致"无法判定通过与否；TimeSpan 模式的字符串中转若无人点名，会带着进入新 codec。
  - 最小修订建议：TP-00 交付物增加显式的 getter（GetDateTime/GetDate/GetTime/GetDateTimeOffset/GetFieldValue/GetValue/GetString）× cType（14/15/22/16/23/26/27）目标行为矩阵，每格标"保持/新增/拒绝"（建议 GetDateTime 遇 TZ 列保持现状并写明文，标为 behavior-keep）；§4.2 TIME 行补 `DbTimeToTimeSpan` 两模式保留且转换改为整数精确路径；TP-A06 按矩阵落行。

  ## 已核对无异议的主要契约（确认范围）

  - **§1 核心验收与机制吻合**：`MathUtil.Round` 在 scale=6 对末位 8/9 tick ≥5 进位后 `new DateTime(num*10)` 可越过 MaxValue.Ticks（`MathUtil.cs:17-31`），与用户"MaxValue 越界、最后整微秒可往返"现象一致；计划如实标注历史根因"缺少当时栈、属源码推断"（§2 末段），未冒充实证。当前 CLR 参数路径在发送 EXECUTE 前拒绝：调用序为 `PrepareInternalCore → BindParameters（内含 NormalizeForWire）→ ExecutePreparedUpdate`（`DmCommand.cs:665-669`、`DmSetValue.cs:1640`），与 §4.4"业务 Execute 发送前失败、Prepare/describe 可以已经发生"完全对应。测试树中确无 DateTime.MaxValue/±1/±9 tick 专项（全仓 grep 核实），§2 该声明属实。
  - **数值算术**：秒内 ticks 0…9,999,999、纳秒上限 999,999,900、不做全 ticks×100（会溢出 int64）均正确；scale 量子表与 `TickQuantumByScale` 一致；interval 打包 scale（subtype≪8|leading≪4|fractional）与 `ResolveIntervalDayToSecondScale` 及测试常量一致；`DmIntervalDT` 的 BigInteger 负值/MinValue 处理属实（`DmIntervalDT.cs:90-93, 1199-1204`，含 `IntervalRejectsTimeSpanMinValueAtMicrosecondScale` 测试）。
